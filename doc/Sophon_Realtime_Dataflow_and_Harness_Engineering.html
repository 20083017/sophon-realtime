02

How task scheduling works

Three distinct schedulers; no general workflow scheduler is implied

2.1 Acoustic turn control

Speech and silence are continuously accumulated. A pause starts a speculative reply and a sequence of separate turn-classification requests. The latter ask stage 0 for one letter, then normalize scores across four choices. The two scores consumed by the active thread are finished and backchannel. A generation counter invalidates answers to obsolete checks. These are internal model scores, not calibrated business confidence.

Default parameter (Tag)ValueEngineering purpose
SOPHON_SPEC_AT / SPEC_MIN_SPEECH0.05 s / 0.3 sEarly draft after enough speech; can be disabled
SOPHON_TURN_CHECKS0.2, 0.35, 0.5, 0.8, 1.3, 2.0 sPause checkpoints (relative to silence onset)
SOPHON_TURN_THRESHOLDS0.95, 0.85, 0.7, 0.5, 0.35, 0.25Progressively lower finish thresholds
SOPHON_TURN_FALLBACK2.0 sFallback reply; optional short-sound suppression is configuration-dependent
SOPHON_RES_TIMEOUT / RETRY_MAX15 s / 3Rollback unconfirmed append, bounded resend; not tool retries

2.2 Inference scheduler vs. policy

The plugin determines what to submit and when; vLLM-Omni owns the actual execution schedule and multi-stage handoff. The turn check runs via a background thread requesting stage 0 through HTTP, rather than advancing the active duplex append fence. The code publishes runner-backed data-plane metadata. This review does not infer the GPU batch ordering, priority policy, KV eviction, or admission algorithm from those flags alone.

2.3 Recovery and priority

Input reservations support commit/rollback. The inspected append loop checks queued exact speech, tool follow-up and failed-append retry before ordinary turn checks, subject to its silence/admission conditions. A resumed utterance can invalidate an earlier draft; a short backchannel can resume a cut answer. A generation fence protects the inference decision, but not automatically a business side effect.

03

Audio and context data flow

What is actually processed by Thinker and what reaches a text backend

Native reasoning is audio-first: the reply prompt carries the current speech plus reconstructed history, instructions and tool schemas. The gateway’s auxiliary ASR is a separate transcript path, not a required intermediate representation for the Thinker. For Tag, stage 0 emits text with optional vocal markup; the stage processor converts the speakable part into Talker tokens, and stage 2 produces audio. Turn-check requests are excluded from speech synthesis.

State or messageProducer / ownerUse
utt, pre, speech_ms, silence_msSophonBufferCurrent utterance buffering and scheduling

last_pb, max_pfTurn classifier consumerBackchannel/finish decision; not default public metadata

Default native history bounds in the inspected Tag code are eight entries and 120 seconds of user-audio duration (with at least one entry retained). This is not a durable business state store. Generated output, gateway emission and actual client playback are separate milestones; engine truncation uses timing estimates unless independently backed by client playback evidence.

Evidence: D:92–93 D:232–279 D:748–756 D:808–895 D:989–1021 P:119–149 R:438–452 O:114–129

For Mario: store observed transcripts, tool results and relevant spoken history with provenance; keep internal counters in control logic, not in the business LLM prompt. Do not invent emotion, emphasis or a semantic turn event just because the model has those capabilities.
04

Native skill / tool calling

Function proposals are not executable skills

The tool subsystem is a compact protocol implementation. It accepts function schemas, adapts them to the model’s chat template, parses generated tool-call JSON, filters control syntax from speech, and publishes call events. Tool calls can be generated before the lead-in has finished playing. It is the client, not the neural model, that implements real service behavior.

ModeActual behaviorDo not confuse with
tool_mode=mockLocal canned responses; max three mock rounds; missing mock can return a generic mock successProduction operations
tool_mode=clientPublish parsed calls; await externally supplied resultsA built-in executor, strict schema validator, or permission engine
Tool bridgeLocal HTTP service, per-key list and condition variable; long-poll drains pending eventsDurable message broker / exactly-once delivery
Tool follow-upAdd result context, schedule new reply when input permitsA persisted task graph or transaction manager

4.1 Protocol example (illustrative values)

Register a narrow function on the Realtime gateway. This is a proposed car-sales tool, not an upstream built-in skill.

{
  "type": "session.update",
  "session": {
    "tools": [{"type":"function", "name":"lookup_inventory",
      "description":"Read inventory for an exact vehicle and store",
      "parameters":{"type":"object", "properties":{
        "vehicle_ref":{"type":"string"}, "color":{"type":"string"}},
        "required":["vehicle_ref","color"]}}]
  }
}

Consume response.function_call_arguments.done, validate the final arguments and execute the real read-only tool. Return the result with the same call ID:

{"type":"conversation.item.create","item":{
  "type":"function_call_output","call_id":"call_demo_1",
  "output":"{\"status\":\"ok\",\"available\":2,\"fixture\":true}"
}}
{"type":"response.create"}

In the inspected gateway, direct outputs are buffered until the subsequent response.create sends them to the engine; only the final output in that batch requests speech. When a call belongs to BackOffice, its result instead resolves the corresponding future. The sample inventory is fictional.

05

GPT-Live delegation

A different facade over the same audio engine

Here the voice model receives a generic delegate(task) tool. The gateway publishes the request for an external client, then accepts commentary and thinking messages keyed to the delegation. It supports model-driven update handling (default) and an optional rule-based mode. The default quiet-window aggregation is 0.6 s and the model-mode initial idle update is 7 s, unless configuration overrides them.

// Gateway -> client (illustrative)
{"type":"session.delegation.created","offset_ms":4200,
 "delegation":{"id":"item_demo_1","type":"delegation",
 "target":"client","task":"查询白色现车库存"}}
// Client -> gateway
{"type":"session.commentary.append","delegation_id":"item_demo_1",
 "content":"查询成功，白色现车 2 辆（模拟数据）"}

The gateway can pass progress/context to the model and let it choose whether to speak or remain silent. A commentary acknowledgment is an acceptance event, not a tool success or playback receipt. The caller must not send results for an obsolete business request merely because a delegation ID still exists.

06

Optional BackOffice: the mini agent Harness

A real bounded reasoning loop, not a full business workflow engine

On the inspected Realtime face, setting SOPHON_LIVE_BACKEND enables a per-session BackOffice. The front model delegates; BackOffice uses a text LLM with the client’s tools. Its context can be configured to use relayed tasks and assistant history, or to include ASR. An asynchronous task handles delegation while the voice-event loop continues.

Harness analogy

BackOffice.run is analogous to an agent’s reasoning–action–observation loop. It receives the task and available tools, asks the LLM what to do next, awaits tool results, appends observations, and repeats until a final answer or a bound. It is a strong reuse reference for Mario; it is not evidence that Mario’s scenario transitions or tool policies can be replaced by model weights.

Performance measurement: instrument audio end → semantic turn decision → first lead-in audio → tool publication → validated execution start/end → result accepted → first fact-bearing audio → playback completion. These timestamps are separate; measuring only first audio can conceal a slow business tool. Use monotonic clocks and correlated IDs, not assumptions about async scheduling.

Recommended first implementation boundary

Do not replace the Sophon turn scheduler with Mario’s text-session logic. Do not enable the upstream optional BackOffice and also call Mario's planner for the same request by default. Use one native audio session and one business state authority. In the initial pilot, use versioned customer-service prompt fragments and narrow read-only catalog/RAG tools. Keep exact-speech Path A for fallback and critical statements, Path B for complex work, Path C for eligible conversation, and test Path D separately.

Skill vs tool: A tool is a callable interface plus a result. A skill is our proposed reusable business capability composed of schema, validation, retrieval/execution, policy, state transition and evaluation. The inspected upstream code supplies the former’s transport and basic loop, not a verified general skill discovery or workflow engine.
